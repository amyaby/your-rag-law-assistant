2

Ingestion pipeline

documents → chunks → 384-d vectors
  • Article-aware chunking first: split at المادة / الفصل / مادة, keep the marker in the content, and only fall back to word windows when no markers exist.
  • Health gate: a PDF with too little text or a bad article/chunk ratio is rejected before it pollutes retrieval.
  • Idempotent writes: re-ingesting the same law updates changed chunks and skips identical ones; the BM25 cache is dropped so it rebuilds on the next query.
Result: 5,844 chunks across 9 laws, all embedded locally with e5-small (384-d) — free, offline, and no API quota wall.
3

Retrieval pipeline

dense + BM25 → RRF → CRAG gate
  • Two independent candidates: dense cosine over the 5,844 vectors and BM25 over the same chunks. Their scores are fused by rank (RRF), so they never need to be on the same scale.
  • Admission is OR: a chunk enters if sim ≥ 0.78 or its BM25 score is ≥ 60% of the best — this is what rescues exact legal nouns.
  • CRAG is conditional: only when the best dense similarity is below 0.78 does the system fetch adala / ism / web in parallel (8s cap) and merge those sources.
Hybrid made retrieval right, not faster. The latency win came from parallel CRAG + an 8s timeout + retries; a healthy local answer logs roughly retrieve_ms≈412 · total_ms≈1583.
4

Generation & persistence

context + memory → answer → two rows
  • Three Gemini calls per turn: optional rephrase, the answer, then the follow-up suggestions. Retries use 3 attempts with exponential backoff and up to 3 fallback models.
  • Memory is prompt stuffing: the last 6 messages (3 turns) are truncated to 600 chars each and wrapped in <turn> tags — labelled as context, not instructions.
  • Persistence is minimal: only role + content are saved. Sources live in the response, so reopening a conversation shows the answers but not the citations.
No answer cache yet. Every turn pays the Gemini latency; caching is the next cheap win, not a bigger model.
5

Conversation memory

server-side · sliding window · 3 turns
  • The browser stores one string — the active conversation id. The transcript itself lives in PostgreSQL, so a reload or a new device can restore it.
  • Sliding window: get_messages(limit=12) loads the window, then _history_block keeps the last 6 messages, 600 chars each.
  • Memory does not touch retrieval: the rephrase and retrieval steps never see the history; only the generation prompt does. Follow-ups rely on the previous answer being in that prompt.
Known bug: the slice uses history[-memory_turns:] instead of [-memory_turns*2:], so the effective window is 3 turns, not 6.
