The one-sentence story: documents are chunked on legal-article boundaries and embedded once; each question is embedded and matched with two complementary retrievers (meaning + exact words), fused by rank, and only if the semantic match is weak do we go out to the web. The answer is generated strictly from the retrieved context with law-qualified citations.

What happens, step by step

  1. Load the raw file (.pdf via pdfplumber, .txt/.html direct).
  2. Health check – reject broken-font PDFs before they pollute the DB (a common Arabic-PDF trap).
  3. Normalize Arabic – unify alef/yaa forms, strip tatweel, fix digits split by RTL rendering (e.g. المادة\n 6).
  4. Split on article markers – each المادة N becomes one semantic unit, so citations map cleanly to a chunk.
  5. Window oversized articles – anything over 4000 chars is cut with 200-char overlap so no sentence is lost at the seam.
  6. Embed with the passage: prefix and unit normalization (so cosine = dot product).
  7. Upsert idempotently – UNIQUE(law, article, md5(content)) means re-ingesting only rewrites changed chunks.
  8. Invalidate the BM25 cache so the lexical index reflects the new corpus.
5,864 vs 5,844: insert_chunks returns len(data) even when rows hit ON CONFLICT DO UPDATE. So the run reports 5,864 attempted rows while the table holds 5,844 distinct chunks. It is a cosmetic reporting mismatch, not data loss.

RetrieverCapturesStrengthWeakness
Dense (pgvector)Meaning / paraphrase"إنهاء عقد" ≈ "فصل تعسفي"Misses exact numbers, rare terms
BM25 (lexical)Exact words / article numbersFind "المادة 60" preciselyNo synonym understanding

Why RRF (Reciprocal Rank Fusion)?

Cosine similarity lives in [0,1]; BM25 is unbounded (can be 0 to 30+). You cannot add or average them fairly. RRF throws away the raw scores and keeps only the rank each document got in each list:

RRF(doc) = w_dense / (k + rank_dense) + w_bm25 / (k + rank_bm25), with k=60.

OR-admission (not AND): a chunk is admitted if it is semantically close OR lexically strong. A BM25-only winner has dense similarity 0.0, so an AND rule would silently drop the exact-match hits that BM25 exists to catch.

Why corrective at all?

If the corpus genuinely does not contain the answer (or the wording diverges badly), the top semantic hit is weak. Instead of hallucinating, we go fetch fresh text from trusted Moroccan sources, keep only the relevant fragments, and feed those to the generator.

Gate uses best DENSE similarity, not the RRF score. This is deliberate: RRF is a rank-only construct with no absolute scale, so it cannot tell you "how confident" the match is — cosine can.
Planned improvement — source origin: tag each returned source with origin: db | web | commentary and render a badge in the UI, so the user (and the prompt) can treat scraped text as unverified.

Combines lists by ∑ 1/(k+rank). Rank-only because cosine [0,1] and BM25 (unbounded) are incomparable.
