ConceptDetail
NameServer-side, sliding-window conversation memory (last-N messages)

Survivesrefresh and a different device (transcript is in PostgreSQL)
Two limits worth stating honestly.
1) Memory does not affect retrieval. rephrase_query(question) and retrieve() never see history, so a vague follow-up can still retrieve the wrong article.
2) Window is effectively 3 turns, not 6. main.py loads 12 messages, then _history_block keeps only the last 6 messages — the constant is named memory_turns but is applied to messages.

4 · Reload / open an old conversation — read-only, no LLM

sequenceDiagram autonumber participant B as Browser app.js participant LS as localStorage participant API as FastAPI participant DB as PostgreSQL B->>LS: getItem ACTIVE_KEY LS-->>B: conversation id B->>API: GET /conversations/id API->>DB: SELECT role, content FROM messages WHERE conversation_id ORDER BY id LIMIT 200 DB-->>API: full transcript API-->>B: messages array B->>B: rebuild bubbles, sources not stored so no source panel
This path costs one SQL query: no embedding, no Gemini, no CRAG. It is why reopening a conversation is instant while asking a new question is not.
Known limitation from README.md: the transcript stores the answer text only. Reopening restores answers but not their sources, so old answers show no source accordion.

6 · Why replies were slow before hybrid

flowchart TD Q[User question] --> RP[Gemini rephrase] RP --> D[Dense-only retrieval] D --> GATE{best dense below 0.78} GATE -- often, weak lexical recall --> CR[CRAG scraping] CR --> S1[adala fetch pages] S1 --> S2[ism fetch pages] S2 --> S3[web search .ma] S3 --> GEN[Gemini answer] GEN --> SUG[Gemini suggestions] GEN -.-> RETRY[429/503 retries with backoff] SUG -.-> RETRY RETRY --> SLOW[Seconds to tens of seconds]
1. Serial CRAG fetch (the big one)
Before the D3 fix, corrective_search fetched up to 4 pages one after another with timeout=10 → up to 40 s per scraper, and the chain tries adala → ism → web. Fix: ThreadPoolExecutor + one shared requests.Session + web_timeout=8 → worst case ~8 s.
2. CRAG fired too often
Dense-only retrieval missed exact legal nouns and Darija/Arabizi wording, so best_dense < 0.78 and the network path opened on many questions. BM25 surfaced the exact-term chunk, so more questions were answerable from the local index.
3. Three sequential Gemini calls
rephrase_query + generate_answer + generate_suggestions. Each is a network round-trip; the rephrase alone measured around 5.7 s in this environment.
4. Retry + fallback backoff
llm_max_attempts=3 per model, llm_backoff_base=1.6, up to 3 models. A 429/503 sleeps 1.6^n before retrying — correct for resilience, expensive in wall-clock time.
5. No answer cache
The rephrase result is cached, but answers are not (F4 still open), so asking the same question twice pays the full generation cost again.
6. Ingestion was slow too (different phase)
Gemini embeddings were one API call per chunk for thousands of chunks, plus the 100 req/min quota. Local e5 removed that from ingestion; it never affected query latency.
Honest framing: hybrid did not make the retrieval step itself faster — it runs in the same milliseconds. It made retrieval right more often, which reduced how often the expensive fallback was needed. The measured latency win came from the CRAG parallelisation, the 8 s timeout, and disciplined retries. Healthy request in the logs: retrieve_ms=412 total_ms=1583.
Current timing bug: retrieve_ms is measured from request start to t_gen, so it includes rephrase + memory + retrieval + CRAG. It is mislabelled; it should be split into pre_gen_ms and a true retrieval time.
