1 · Ingestion: how are the PDFs processed?

Ingestion is normally a batch/admin process, separate from answering user questions. A batch can include many PDFs. Each file goes through the same logical stages; files can be processed sequentially or concurrently depending on the code.

PDF batch

2 · User query: dense and BM25 retrieval

Dense retrieval and BM25 are separate search paths. They can run simultaneously if the backend starts both tasks before waiting for results. If the code awaits one before starting the other, they run sequentially. The architecture alone cannot confirm which your code does.

User question

3 · After retrieval: prompt → LLM → response

STEP 1

Build prompt

Backend combines the question, retrieved legal chunks, instructions to answer from evidence, and any relevant conversation history.

STEP 2

Call the LLM

The discussed generator is Gemini. It reads the supplied prompt and drafts an answer; it does not automatically know which legal source is authoritative unless evidence is supplied.

STEP 3

Return + save

Send the answer to the user. The app may save both user and assistant messages. Conversation history/checkpoints are separate from the legal vector index.

What if retrieval finds no good evidence?

A trustworthy legal RAG should avoid inventing a confident answer. It can check a threshold, say the sources are insufficient, ask for clarification, or direct the user to an authoritative source. The exact fallback depends on your code.

4 · RRF, with a tiny example

RRF uses rank positions—not the raw dense similarity or BM25 scores.

ChunkDense rankBM25 rankInterpretation
A15Great semantic match, weaker keyword match
B21Strong in both lists; likely ranks well after fusion
C—2Strong lexical result, absent from dense candidates
D3—Strong semantic result, absent from BM25 candidates
Formula: RRF(chunk) = Σ weight / (k + rank). Discussed configuration: k=60, dense weight 1.0, BM25 weight 0.35. A chunk missing from a list contributes nothing from that list in a common implementation.
